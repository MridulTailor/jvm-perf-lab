# JVM Performance Lab (`jvm-perf-lab`)

An empirical, reproducible JVM performance engineering laboratory evaluating HotSpot C2 compiler optimizations (Escape Analysis, Scalar Replacement, Inlining, Devirtualization) and Garbage Collection dynamics (Serial, Parallel, G1, ZGC, Generational ZGC, Shenandoah) on Apple Silicon (AArch64) under Amazon Corretto 21 LTS.

---

## Key Performance Findings

All metrics below are derived directly from raw benchmark artifacts (`results/raw/`) generated by automated scripts.

1. **Escape Analysis & Scalar Replacement**:
   - Enabling C2 Escape Analysis (`-XX:+DoEscapeAnalysis`) increased throughput by **+198.8%** (from `259,108 ± 2,494` to `774,148 ± 13,717` ops/s; 3 forks).
   - Eliminated **48,000.0 B/op** of heap allocation (dropping allocation to `0.009 B/op`).
   - Source: [`results/raw/jmh/ea_default.json`](results/raw/jmh/ea_default.json), [`results/raw/jmh/ea_disabled.json`](results/raw/jmh/ea_disabled.json).

2. **Polymorphic Dispatch & Devirtualization**:
   - Monomorphic call site inlining delivered **10.4x higher throughput** than a 4-receiver megamorphic call site (`3,191,723 ± 18,257` vs `306,429 ± 14,855` ops/s; 3 forks).
   - Demonstrates the steep cost of speculative inlining failure and `itable` stub dispatch.
   - Source: [`results/raw/jmh/inlining_default.json`](results/raw/jmh/inlining_default.json).

3. **Inlining Bytecode Budget Heuristics**:
   - An unrolled method of 422 bytes exceeded HotSpot's `FreqInlineSize` (325 bytes) and was rejected by C2 (`hot method too big`).
   - Expanding inline thresholds (`-XX:MaxInlineSize=100 -XX:FreqInlineSize=500`) allowed inlining, boosting throughput by **+14.8%** (`197,757` to `227,090` ops/s), matching the small-methods pipeline (`227,253` ops/s).
   - Disabling inlining (`-XX:-Inline`) imposed a **24.4% throughput penalty**.
   - Source: [`results/raw/jit/inlining_jit.log`](results/raw/jit/inlining_jit.log), [`results/raw/jmh/inlining_thresholds.json`](results/raw/jmh/inlining_thresholds.json).

4. **Garbage Collection Pause Latencies (2GB Heap)**:
   - **ZGC**: p99 pause of **0.019 ms** (19 µs) and max pause of **0.030 ms** with **0.004% GC overhead**.
   - **ZGC Generational**: p99 pause of **0.014 ms** (14 µs) and max pause of **0.021 ms** with **0.005% GC overhead**.
   - **Shenandoah**: p99 pause of **0.192 ms** with **0.048% GC overhead**.
   - **G1**: p99 pause of **4.875 ms** with **0.906% GC overhead**.
   - **Parallel**: p99 pause of **6.839 ms** with **2.320% GC overhead**.
   - **Serial**: p99 pause of **17.138 ms** with **6.301% GC overhead** (max pause 234.9 ms).
   - Source: [`results/processed/gc_summary.csv`](results/processed/gc_summary.csv), [`docs/gc_pauses.svg`](docs/gc_pauses.svg).

## Environment & Setup

- **Hardware**: Apple Silicon (Apple M1 Pro, AArch64, 8 physical cores, 16 GB RAM).
- **Operating System**: macOS 15.3.2 (Darwin 24.3.0).
- **JDK**: Amazon Corretto 21 LTS (`21.0.12.12.1`, OpenJDK 64-Bit Server VM).
- **Profiling Tools**: `async-profiler` 4.5 (`asprof`) and JDK Flight Recorder (`jfr`).
- **Python**: Python 3.13 (standard library only; zero pip dependencies required).

### Prerequisites
1. Ensure Java 21 (Amazon Corretto recommended) and Maven are installed:
   ```bash
   mvn -version
   java -version
   ```
2. Capture environment details:
   ```bash
   ./scripts/env_capture.sh
   ```

## How to Reproduce

### 1. Fast End-to-End Smoke Test (< 5 minutes)
Runs the entire pipeline end-to-end in QUICK mode (unit tests, quick JMH benchmarks, quick GC runs, JIT diagnostics, warmup curves, profiling, and report generation):
```bash
./scripts/smoke.sh
```

### 2. Run Full JMH Microbenchmarks (~13.5 minutes)
Executes 3 forks, 5 warmup iterations, and 10 measurement iterations with allocation profiling (`-prof gc`):
```bash
./scripts/run_jmh.sh FULL
```

### 3. Run Full GC Evaluation Matrix (~38 minutes)
Executes 36 isolated JVM runs (6 collectors × 2 heap sizes × 3 repetitions) with unified GC logging:
```bash
./scripts/run_gc_bench.sh FULL
python3 scripts/parse_gc.py --dir results/raw/gc --output-csv results/processed/gc_summary.csv --output-json results/processed/gc_summary.json
python3 scripts/plot_gc.py
```

### 4. Run JIT Diagnostics & Warmup Curve
```bash
./scripts/run_jit_diagnostics.sh
./scripts/run_warmup.sh FULL
```

### 5. Run Profiling (CPU & Allocation)
```bash
./scripts/run_profile.sh FULL
```

### 6. Regenerate Documentation
```bash
python3 scripts/report.py
```

## Limitations

1. **Single Machine Hardware**: All measurements were performed on a single machine powered by Apple Silicon (Apple M1 Pro, AArch64).
2. **Microbenchmarks vs Production Workloads**: Microbenchmarks isolate specific HotSpot compiler and GC subsystems in controlled loops; production applications possess distinct allocation patterns, object lifecycles, and I/O concurrency.
3. **Architecture Specificity**: Results recorded on AArch64 Apple Silicon reflect its unified memory architecture, large L2 cache hierarchy, and specific memory consistency model; measurements may not generalize directly to x86-64 server architectures or AWS Graviton processors.
4. **Synthetic Old-Gen Pressure**: The retention fraction in `AllocationHeavy` utilizes a bounded circular buffer to induce predictable tenured space survival; production applications often exhibit more diverse object death rates.
